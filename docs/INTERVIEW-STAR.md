# AI Agent 后端服务 面试 STAR 讲稿（全部数据可复现）

> 本文所有数字均在本地实测跑出，复现命令见文末。脚本运行结果跑过三轮，延迟数据稳定。

## 30 秒版

这是一个 FastAPI + LangGraph 的 AI Agent 后端：LangGraph 用图编排多轮对话，支持 ReAct 工具调用、RAG 知识库、SSE 流式输出、JWT 鉴权和 Docker Compose 一键部署。我在这个项目上做的最有价值的一件事，是**把「Redis 降级」这个我以为没问题的设计挖出了性能缺陷**：

第一次测发现登录 **8154ms** —— 降级逻辑是对的，但 Redis 客户端没设超时，每次调用要挂到系统级 TCP 超时。加 0.5s 超时后降到 1240ms；但我发现这只治了一半：超时只是给单次调用封顶，一次登录要碰 Redis 2–3 次，连乘起来还是秒级。于是又加了熔断器 —— 连续失败后短期内直接跳过 Redis。最终 `/health` 稳态从 510ms 降到 **1.6ms**、登录从 1262ms 降到 **223ms**，同一套测试从 177.66 秒跑到 17.84 秒，快了 **10 倍**。

## STAR 主线

**Situation（情境）**
AI 后端区别于普通后端的一点：它有**辅助组件依赖**（Redis 做限流和登录失败锁定、向量库做 RAG）。这类组件的通行写法是"不可用就降级放行，别拖垮主流程"——我当时也是这么设计的，还专门写了注释。

**Task（任务）**
给项目做一轮真实验证：测试覆盖率到底多少、接口延迟到底多少、这些"我以为没问题"的降级路径在故障场景下到底表现如何。

**Action（行动）**
1. 独立虚拟环境装依赖，跑全量 pytest（不依赖 PostgreSQL / Redis / 真实大模型，测试用内存 SQLite + 假 LangGraph 图）。
2. 写基准脚本：REST 接口 P50/P95、bcrypt 认证链路、会话 CRUD、SSE 首字节与逐 token 节拍、并发吞吐。
3. 单独压**故障场景**：在**无 Redis 环境下**重复请求 `/health` 和 `/auth/login`，量化降级路径的实际延迟。
4. 定位两轮根因 → 修复 → **每轮都做阳性对照**（把修复回退，确认新写的测试真的会红，而不是写了个永远通过的测试）。
5. 补齐 HTTP 层的防护回归（原本只有单元级限流测试）。

## 两轮根因：同一个认知误区被挖了两层

| 轮次 | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 第一轮 | Redis 不可用时认证链路拖到 **8154ms** | `aioredis.from_url()` 未设 socket 超时，每次调用等到系统级 TCP 超时 | 新增 `REDIS_CONNECT_TIMEOUT_SECONDS` / `REDIS_SOCKET_TIMEOUT_SECONDS`（默认 0.5s），并 `retry_on_timeout=False` |
| 第二轮 | 加上超时后仍 **1240ms** | 超时只给**单次调用**封顶，但一次登录要碰 Redis 2–3 次（限流 + 锁定查询 + 清除），延迟是连乘的 | 新增 Redis 熔断器：连续失败 3 次即熔断 30s，期间直接返回降级值，冷却结束后放行一次半开探测 |

**两轮的核心认知**：降级保证的是**正确性**（不会因 Redis 挂了导致登录全失败），没有保证**延迟**。这两件事是完全独立的——语义对了，用户看到的还是转圈。第一轮我改到"单次调用不死等"就以为结束了，是压测数据告诉我还差一层。

## 熔断的行为（逐次调用实测曲线）

同一进程内两阶段对照，前几次"付学费"，之后断崖式下降：

```
有熔断  GET /health : 516  512  508    2    2    2    2    1   ms
无熔断  GET /health : 514  509  511  513  514  508  510  508   ms
有熔断  POST /login : 1239 768  214  239  219  219             ms
无熔断  POST /login : 1268 1219 1248 1277 1243 1282            ms
```

- `/health` 前 **3** 次、`/login` 前 **2** 次仍需付满超时（连续失败未达阈值），此后一律短路
- 稳态只剩业务本身的成本：登录剩 223ms ≈ **bcrypt 校验的真实开销**，说明 Redis 延迟已被完全消除
- 6 次登录总耗时：2899ms vs 7536ms

## 顺带补的验证（非缺陷，是验证缺口）

- `tests/test_cache_timeout.py`：把超时上限钉死，防止有人改回无超时写法。
- `tests/test_protection_http.py`：原来的限流测试是**单元级**（直接调 `is_allowed`），接线断掉也测不出来。补了 HTTP 层：对话/登录超限真返回 429、`TRUST_PROXY=False` 时忽略伪造 `X-Forwarded-For`、`True` 时取最左原始 IP、跨用户访问会话返回 404（而非 403，不泄露资源存在性）。
- `tests/test_redis_circuit.py`（本次新增 6 条）：连续失败达阈值才打开、熔断期间**根本不发起调用**（不是发起了再失败）、偶发失败会被成功清零不累积误伤、冷却后半开探测成功即闭合、健康检查熔断期直接报 down、运维开关 `REDIS_CIRCUIT_ENABLED=False` 可绕过。

### 一个我自己制造、又自己发现的问题

加熔断后跑全量回归，**3 个限流测试反而失败了**。排查后确认：熔断状态是进程级共享的，前面积累的失败把限流用例注入的 Redis 替身短路了，用例退化成"永远放行"的假阳性——**断言 429 反而通不过**。这件事反过来证明了新测试是真护栏（它们能感知到行为变化）。

修法是在 conftest 加一个**非 autouse** 的 `redis_closed` fixture：凡是注入了可用 Redis 替身的用例，显式引用它声明"本用例 Redis 可用"。刻意不做成 autouse，否则每个用例都复位会让套件耗时退回熔断前水平。这个权衡写进了 fixture 的 docstring。

## 可能的追问与回答

- **"熔断了是不是限流和登录锁定就失效了？"**
  是的，必须承认：这是**可用性换安全能力**的取舍。熔断期间攻击者的爆破尝试不会被计数锁定。我的理由是——Redis 已经连续 3 次连不上，说明它现在根本提供不了这个能力，与其让每个正常用户都等 1.2 秒，不如先保住主流程。30 秒冷却时长就是这两个风险的折中，并且配置化了（`REDIS_CIRCUIT_COOLDOWN_SECONDS`），运维可以按实际 Redis 恢复时间调。**真正要求不可降级锁定的场景不该这么设计。**
- **"为什么不一开始就熔断？"**
  因为顺序反了会掩盖问题。先用超时把单次调用从"挂到系统级 TCP 超时"变成"0.5 秒内必返回"，熔断才有确定的收益；若没有超时兜底就去熔断，那么用于触发熔断的前几次调用仍会把服务拖到几十秒级，掩盖真实延迟成本。分两步做，每步独立可验证、可回退。
- **"阈值 3 次、冷却 30 秒怎么定的？"**
  阈值 3 是想覆盖"一次登录碰到 Redis 2–3 次"这个倍数——第一个请求付学费，第二个请求开始受益；冷却 30 秒对应 Redis 常见恢复时间。这两个数字是拍的，但都做成了配置项，可以拿真实运维数据回头调。我没做过压测调参，如实说。
- **"SSE 首字节 37ms 里有多少是框架，多少是模型？"**
  实验里模型是假的、固定 20ms/token：所以 TTFB 37ms 几乎全是框架路径（鉴权 + DB 加载历史 + 图准备 + 序列化）的开销；token 间隔 31.06ms 中约 11ms 是框架抖动。**真实模型的推理耗时不在这些数字里**，这点必须说清楚。
- **"并发只有 219 req/s？"**
  这是本机、单 worker、SQLite 写为主的场景；同步 ORM 已放到线程池避免阻塞事件循环，但 SQLite 本身不适合做高并发基准。生产换 PostgreSQL + 多 worker 是另一回事，我没有跑过，不报数字。

## 不能夸大的

1. 所有延迟是**本机回环**数字，不代表生产（真实网络、真实模型、PostgreSQL）。
2. SSE 数字用**假模型**测得，只反映框架路径开销，不含真实推理。
3. 基准环境无 Redis，因此 Redis 相关接口的数字是「降级态」的；Redis 正常时这些接口会更快（未实测，不报）。**但反过来要充分说明：这些数字衡量的是"Redis 全挂"的最坏情况，这是有意为之的故障注入，不是常态。**
4. 熔断的稳态收益建立在"Redis 持续不可用"的前提上。Redis 正常时熔断从不触发，这一整套改动对正常路径零影响（也零收益）。
5. `health` 稳态降到 1.6ms 的前提是数据库探针走 SQLite 内存库很快；生产换成 PostgreSQL 后 `/health` 的基线会由 DB 探针决定，不是这个数字。
6. 覆盖率 87% 是行覆盖率，不等于"测到了所有行为"；`agent/graph.py`、`checkpointer.py` 仍只有三成，依赖真实 LLM 编排的部分未被覆盖。
